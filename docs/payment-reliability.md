## 1. 当前支付主路径（已实现）

```text
createOrder（可顺带 JSAPI）
  → 小程序 uni.requestPayment
  → 或再次 orderPay 拉起支付
  → 微信异步 POST /wechat/pay/notify
  → 验签 → NotifyLogic 将订单 status 改为 1
```

另外：

- 积分商品 / 月结客户：建单时直接 `status=1`，不走微信回调  
- 预支付参数：`OutTradeNo = order_sn`，`TimeExpire = 30 分钟`（微信侧过期）  
- Debug 时可把金额打成 1 分（`wechatPay.debug`）

**定位**：演示/中小项目可用的主链路，**不是**完整生产级支付风控与对账体系。

## 2. 现状对照表（异常场景）

| 异常场景 | 当前是否处理 | 实现情况 | 风险 |
|----------|--------------|----------|------|
| **回调伪造** | 有 | `PaidVerifySign` 验签失败回 FAIL | 低（依赖验签实现正确） |
| **回调重复** | 部分 | 已是 `status==1` 则直接成功返回（幂等） | 中：无行锁/条件更新，极端并发仍可能竞态 |
| **重复点击支付** | 弱 | 已支付拒绝 `orderPay`；未支付可多次拉 JSAPI，一般同 `order_sn` | 中：依赖微信同单号策略 |
| **掉单**（用户已付款，本地仍 `status=0`） | **无** | 无主动查单、无补单任务、无对账 | **高** |
| **回调丢失后补偿** | **无** | 仅靠微信重试；重试失败则一直未付 | **高** |
| **金额被篡改/不一致** | **无** | 回调写入 `finish`，**未与 `order.total` 比对** | **高** |
| **重复扣款** | **未专门设计** | 无独立支付流水表；注释「生成流水」为空 | 中高 |
| **超时关单 vs 支付成功冲突** | **无** | 字段有 `status_cancel=3`，未见定时关单；无关微信单 | 中高 |
| **已支付取消退款** | **无** | `CancelOrder` 注释要退款，实现只改取消字段 | **高**（客诉） |
| **建单事务一致性** | 弱 | `Begin` 后部分写仍用 `global.DB` | 中 |
| **库存与支付** | 弱 | 建单即扣库存；未支付超时不自动回滚库存 | 中 |

## 3. 已有能力说明（避免误判）

### 3.1 回调验签（有）

`PayNotify`：绑定 XML → `PaidVerifySign` → 校验 `ReturnCode` / `ResultCode` → `NotifyLogic`。

伪造回调在验签正常的前提下会被拒。

### 3.2 回调幂等（有，但不强）

`NotifyLogic`：

- 订单不存在 → 失败  
- `status == 1` → 视为已处理，返回成功（避免微信一直重试）  
- `status != 0` → 失败  
- 否则写 `finish`、`status=1`、`pay_time`、`payment_openid`、`transation_id` 等  

未使用 `UPDATE ... WHERE status = 0`，也未用悲观/乐观锁。

### 3.3 微信预支付过期（有，仅微信侧）

`TimeExpire` 30 分钟只影响微信能否继续付，**不会**自动把本地订单标超时取消，也**不会**自动恢复库存。

## 4. 二次开发建议补全（按优先级）

### P0 — 接单前强烈建议

| 项 | 做什么 | 解决什么 |
|----|--------|----------|
| **金额校验** | 回调中比较 `TotalFee`（分）与订单应付金额，不一致告警并拒绝改状态 | 防错账/异常通知 |
| **条件更新** | `UPDATE shop_order SET status=1,... WHERE id=? AND status=0`，影响行数为 0 则当幂等成功 | 并发回调安全 |
| **主动查单补单** | 定时任务：扫描长时间 `status=0` 的单，调微信「查询订单」；若已支付则走与回调相同的入账逻辑 | **掉单** |
| **支付成功入账事务** | 改订单状态 + 写支付流水（新建表或完善现有财务流水）同一事务 | 可追溯、对账 |

### P1 — 完整商用体验

| 项 | 做什么 | 解决什么 |
|----|--------|----------|
| **超时关单** | 如 30 分钟未付：`status_cancel=3`，回滚库存；并关/作废微信侧未支付单（若有接口） | 超时与库存 |
| **关单与支付成功冲突** | 关单用条件更新；补单时若发现微信已付而本地已取消 → **自动退款或人工工单**，禁止静默不一致 | 超时冲突 |
| **退款闭环** | 取消已支付、售后同意退款时调微信退款 API，回写 `status_refund` / 售后单 | 注释里未完成的退款 |
| **管理端「同步支付状态」** | 运营一键按订单查微信并补状态 | 客服救急 |

### P2 — 增强与规范

| 项 | 做什么 |
|----|--------|
| 支付流水表 | `order_id`、`order_sn`、`transaction_id`、金额、状态、原始回调摘要、唯一索引防重 |
| 告警 | 掉单补单失败、金额不符、退款失败 → 日志/企微/邮件 |
| 建单事务收紧 | 订单、明细、扣库存、清购物车全部走同一 `tx` |
| 多规格/余额支付 | 与微信同等的幂等、对账策略 |
| 文档与配置 | 每客户独立 `notifyUrl`、商户号；回调必须 HTTPS 公网 |

## 5. 建议的目标状态机（支付相关）

```text
待支付(status=0)
  ├─ 支付成功(回调或查单补单) ──► 已支付待发货(status=1)
  ├─ 超时关单 ──► 取消(status_cancel=3) + 回库存
  └─ 用户取消 ──► 取消(status_cancel=1)；若此时微信已扣款 ──► 走退款

已支付后取消/售后 ──► 退款中 ──► 已退款/失败（写 refund 字段 + 流水）
```

关键原则：

1. **微信结果为准做对账，本地状态可补，不可长期与微信不一致**  
2. **所有改状态用条件更新，保证幂等**  
3. **钱货（库存）变更可追溯（流水）**

## 6. 接单话术边界（建议）

对外可说：

- 支持微信小程序支付、支付回调更新订单  
- 可按需做支付对账、掉单补偿、退款（需列入定制/工期）  

不建议首期就承诺「金融级支付系统、零掉单、复杂分账」——当前底座未具备，需按上面清单开发后才能写进合同。

| 阶段 | 建议 |

## 8. 一页结论

| 问题 | 答案 |
|------|------|
| 现在能不能付？ | 能（配置好商户号与回调的前提下） |
| 异常是否都处理了？ | **没有**；验签和简单幂等有，掉单/对账/退款/超时冲突基本没有 |
| 二次开发先补什么？ | **金额校验 + 条件更新 + 定时查单补单 + 支付流水**，然后是退款与超时关单 |
