# 订单标识：自增 `id` vs `order_sn`（迁移风险）

> 记录点：C 端订单操作（详情 / 取消 / 支付 / 确认收货）普遍用 `shop_order.id`；讨论「数据迁移后 id 变化会不会错单」。  
> 相关：[03a-order-pay.md](./03a-order-pay.md)、[todo-gaps.md](./todo-gaps.md) GEN-04、[fulfillment v0.3.0](./features/fulfillment/v0.3.0/server/design.md)（确认收货仍用 `ID`）。

## 1. 两个字段分别是什么

| 字段 | 角色 | 现状 |
|------|------|------|
| `id` | 表主键，自增 | 小程序路由 `?id=`、`findOrder` / `cancelOrder` / `orderPay` / `confirmOrder` 都传它；发货单、售后表外键也是 `order_id → id` |
| `order_sn` | 业务单号（如 `SN...`） | 下单生成；微信 `out_trade_no`、支付回调/查单按它找单；给客服/用户看 |

**业务上 `order_sn` 应当唯一**，但建表时 **没有 UNIQUE 索引**，库不强制。

## 2. 风险：怕的是 id 被重排，不是自增每天会变

同库持续运行、整库 dump/restore、迁移时 **INSERT 带上原来的 `id`**，主键不变，站内引用不会断。

会出问题的操作：

- 两套商城库合并，两边都有 `id=100`
- 导入时丢掉原 id，让新库重新自增
- 把 `id` 给了外部系统（导出表、别的服务存了 `order_id=123`）

此时凡靠 `id` 串起来的都会错位：小程序收藏链接、`shop_order_delivery.order_id`、`shop_order_return.order_id` 等。漏映射一张表就会「点开订单不是那一单」。

`order_sn` 不依赖自增，迁移后字符串还在就能对上微信账单、客服查单。它更适合当**跨系统身份**。

## 3. 为什么当前接口仍用 `id`（含 M2-3）

- C 端整条链路已经是 `id`，确认收货再单独改成 `orderSn` 并不能让迁移变安全（取消/详情仍用 id）
- `id` 是主键，站内关联、条件更新最快
- 单商户独立部署、搬家时保留 id，风险可控

M2-3 对齐断路由，**不在本切片切换标识**。

## 4. 若要降低迁移风险（后续，非默认必做）

建议整包做，不要只改一个接口：

1. `order_sn` 加 **UNIQUE**（先查重再加索引）
2. 迁移规范：**保留原 `id`**，或提供旧 id → 新 id 映射并改所有外键
3. 对外/可导出 API 逐步支持 `orderSn`（或只暴露 sn）
4. 生成算法保证跨库不撞号（前缀/机器位/时间），不能只靠自增

缺口编号：**GEN-04**（见 todo-gaps）。优先级 P2：首期单库交付可缓。
